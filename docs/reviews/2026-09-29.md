**① CONFLICT — queue ordering model, inside action-visual-lifecycle.md (and vs shipped engine).**
The doc still carries the ABANDONED FIFO framing in three places:
- Core Rule 4 (line 17): "Tics are display values, not a timing mechanism. The queue is a linked
  list ordered at INSERTION time — no global sort, no re-ordering. Tics help the player read
  timing but do NOT drive processing."
- §10 (line 389): "Tics are display values only. They help the player read timing. They do NOT
  drive processing order — insertion order does."
- Glossary **Tic** (line 426): "Display-only countdown value ... never drives processing order."

But the SHIPPED engine contradicts all three. js/combat/tic-queue.js (line 3–6): "`tics` is an
ordering key only: each new row is spliced into tics-ascending position once, at insert, and the
array is never globally re-sorted ... Head = first non-ready row in that frozen array order."
Tics DO determine order (head = lowest-tics actionable row), and this is the user-confirmed
design — workorder-2026-09-28-queue-sorted-insert.md explicitly calls FIFO append "❌ WRONG"
(line 31) and mandates "the queue MUST be ordered by tics (soonest-to-act on top)" (line 91).
Same doc action-visual-lifecycle.md ALSO says the correct thing elsewhere (line 322: "Each item
is placed at its correct position when added"; line 380: "placed at the correct position when
added — no global re-sort"), so it contradicts itself and the code.
Recommendation: rewrite Core Rule 4 / §10-last-sentence / Glossary-Tic to "tics IS the ordering
key; rows are placed at tics-ascending position once at insert and the array is never globally
re-sorted; head = first non-ready row in that frozen order." This is an edit Spahrep should
confirm/capture (the ruling is already implemented and shipped but has no PC-DEC entry).
